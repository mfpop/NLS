# ERP Import — Architecture & Rules (Handoff)

## Overview

Two ERP import systems coexist:

1. **Manufacturing (legacy)** — `ErpImportPattern` in `manufacturing` app. Full CRUD with scope, plant/department/resource-group selection, field mappings, job workflow with state machine. Used by the old Erp Pattern page.

2. **Data Management (current)** — `ErpPattern` in `data_management` app. Simplified: no scope, no entity selection, no state machine. Import is operation-focused: select pattern → validate → import/update. This is the frontend ERP Import page.

## Service Boundaries

### ErpPatternService
- CRUD for patterns + mapping validation
- Validates: empty mappings, duplicate source/destination names, unsupported destination entity
- Does NOT parse files, does NOT touch import logic

### ErpSourceFileService
- `upload_file(file, uploaded_by)` — stores file with UUID name inside ERP source folder, creates DB record
- `cleanup_source_files(confirmed=True)` — requires `confirmed`, validates path stays inside source root, marks files DELETED
- `_validate_path_within_source_root()` — path containment guard

### ErpImportValidationService
- **Read-only**. No DB writes, no log creation, no file deletion.
- Returns `ValidationResult { status, errors, warnings, missing_fields, source_file, pattern }`
- Statuses: `MISSING_FILE`, `MISSING_FIELDS`, `INVALID_FILE`, `READY`, `FAILED`

### ErpImportService
- Owns `transaction.atomic`. Revalidates immediately before write.
- Requires `confirmed=True`. On validation failure → creates FAILED log.
- On exception during apply → creates FAILED log (log always created).
- Updates source file status to IMPORTED/FAILED.

### ErpImportWorkspaceService
- `reset_workspace(confirmed=True)` — deletes source files only, marks DELETED, preserves logs and patterns.
- `refresh_pattern_list()` — returns active patterns.

## GraphQL API

### Queries
- `erpPatterns: [ErpPatternNode!]`
- `erpImportValidation(patternId: Int!): ValidationResultType!`
- `erpImportLogs(patternId: Int): [ErpImportLogNode!]`

### Mutations
- `uploadErpSourceFile(file: Upload!): ErpSourceFileNode!`
- `validateErpPattern(patternId: Int!): ValidationResultType!`
- `executeErpImport(patternId: Int!, confirmed: Boolean!): ImportResultType!`
- `resetErpImportWorkspace(confirmed: Boolean!): Boolean!`

### Resolver Rules
- All resolvers delegate to services immediately
- No `transaction.atomic`, no `open()`, no `.read()`, no `.write()`, no `bulk_create`, no `save()`, no `delete()` in resolvers
- No file parsing, no import logic, no destination validation in resolvers

## Frontend ERP Import Page (SimpleErpImportPage)

### Location
`frontend/src/pages/system/erp-data/erp-import/SimpleErpImportPage.tsx`

### Data Flow
1. Load patterns via `ERP_PATTERNS_QUERY`
2. Load latest import logs via `ERP_IMPORT_LOGS_QUERY`
3. User clicks Validate → calls `VALIDATE_ERP_PATTERN` mutation → shows backend status
4. User clicks Import → calls `EXECUTE_ERP_IMPORT(confirmed: true)` → shows backend counts
5. User clicks Upload → multipart `fetch` to GraphQL endpoint with `uploadErpSourceFile` mutation
6. User clicks Reset → confirm dialog → calls `RESET_ERP_IMPORT_WORKSPACE(confirmed: true)`

### State Rules
- Import button disabled unless validation status === `READY`
- Validate button always enabled (backend validates)
- Upload triggers pattern list refetch
- Reset clears local state, refetches patterns, preserves logs

### Status Display
- `Ready to validate` — muted (default)
- `MISSING_FILE`, `MISSING_FIELDS` — amber
- `INVALID_FILE`, `FAILED` — red
- `READY`, `IMPORTED` — green

### Counts
- Added (green), Updated (blue), Not Updated (amber), Failed (red)
- All from backend `ImportResult` or latest `ErpImportLog`

### Confirm Dialogs
- Import: "Confirm import?" / "Import/update database records using selected ERP Pattern and source file." / "Import / Update"
- Reset: "Reset ERP import workspace?" / "This refreshes patterns, clears selection, and deletes ERP source files only. Logs and patterns are preserved." / "Reset"

## Security

- Uploaded filenames never used as filesystem paths; stored name is UUID + extension
- Path containment validated on cleanup/reset — rejects paths outside ERP source folder
- Unknown file extensions rejected at upload
- Original `file.name` stored in DB but never used for filesystem operations
